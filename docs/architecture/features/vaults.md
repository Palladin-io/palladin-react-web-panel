# Feature: vaults

**Path:** `src/features/vaults/` — the largest feature.

## What it does
Vault and entry management: the core of the product. Users browse vaults, drill into a vault, and open individual entries to reveal/edit decrypted credentials.

## How it's organized
Three nested levels, each a split-view page with its own tab strip:
- **Vault list** → list panel + create/settings flows.
- **Vault detail** — tabs: Entries / Agents / Audit / Members / Settings.
- **Entry detail** — tabs: Details / Agents / History / Logs.

Protocol 2 list/search data comes from `sync/`: after unlock, `MemberSyncProvider` opens the Member Vault key, builds an initial snapshot, applies the closing delta, and then follows incremental deltas. IndexedDB stores only authenticated ciphertext envelopes, structural metadata, and sequence cursors. Decrypted Vault metadata and normalized MemberIndex records live in Zustand memory and are cleared immediately on lock/logout. Entry secrets remain lazy and are never part of Member sync.

After an authoritative ready sync, an unlocked account with no structural default Vault runs a bounded reconciliation attempt using the in-memory Member private key and the canonical encrypted Vault-creation protocol. A successful creation triggers one follow-up sync. Retryable failures use three bounded attempts; a `409 already exists` triggers exactly one follow-up sync and then stops automatic creation for the current unlocked provider session. This resolves a concurrent onboarding creator without creating a create/sync loop around an orphaned or temporarily invisible Vault. Locking or remounting starts a new session, and no key material is persisted by reconciliation.

The Vault list and split-view list panel consume decrypted `MemberVaultMetadata` directly from the in-memory sync store and search names/descriptions locally. The Vault Detail Entries tab likewise projects Active, Archived and Recently Deleted rows from the in-memory `MemberIndex`, including local search/sort and isolated anonymous corruption rows; tombstones and optimistic revisions flow through the same sync store. These surfaces expose locked, syncing, reset and partial-error states without falling back to server-side content search. Entry-detail consumers share the exported detail query. Active entry rows and the entry-detail page own the decrypt-on-demand logic; create/edit flows follow the inline-edit and modal conventions.

Vault Settings reads presentation exclusively from the unlocked Member sync store. Before saving, it fetches and authenticates the latest encrypted Vault summary, opens VK in memory, compares the decrypted metadata with the revision the Member edited and encrypts exactly the next revision. A stale or raced edit is never merged automatically. Custom icons use the shared encrypted-asset pipeline; a failed metadata commit compensates a definite upload, while an ambiguous lost response is reconciled before cleanup so a committed metadata reference is never broken. Superseded assets are removed only after metadata commit. Remote favicon URLs and plaintext image uploads are not accepted.

The Vault Detail Agents tab is exclusively a scoped-grant surface, not a per-Vault Discovery eligibility or synchronization control: every active organization Agent receives encrypted Discovery by protocol design, and provisioning remains background infrastructure rather than user-facing Vault UI. The tab exposes grant creation and scoped grant history, including expired and revoked grants. Protocol 2 GRANULAR grant and regrant actions produce canonical per-Entry envelopes. FULL is explicit whole-Vault trust and carries one current VK sealed to the authoritative Agent public key; VDK and EntryDEK are never disclosed, and delivery remains one audited Entry per operation.

The Vault Detail Members tab reads the structural Member directory in keyset pages of 50 (server maximum 100). It never treats organization membership as Vault membership. `Active`, `Pending`, `WaitingForRotation`, and `BlockedLastMember` are server-owned states; a removal request is never presented as completed before every affected Vault rotation commits. The current Vault stays usable during planned rotation. The organization-wide removal mutation is shared through `shared/api/organization-members-api.ts`, while the Vault feature owns only its tab hook and presentation. Success invalidates both the selected Vault directory and the organization-member cache prefix.

Create Entry uses a server-issued opaque Entry ID and builds MemberIndex, canonical MemberSecret and optional AgentDiscovery from one encrypted Agent Visibility Policy. The UI presents that policy as a simple Discovery eye toggle beside the Entry label and each discovery-safe field; it never exposes internal access-mode dropdowns. Username and URL domain are discoverable by default for Credentials. Secret values, Notes and TOTP never receive a Discovery toggle; post-grant and runtime access rules remain internal. The three projections share revision 1 but use isolated keys and authenticated projection-specific scopes. The request is ciphertext-only and the backend commits the complete projection set atomically.

Entry Detail reads presentation from the in-memory MemberIndex and opens MemberSecret only after an explicit reveal. Edits create the next immutable MemberSecret revision and include MemberIndex or AgentDiscovery only when their canonical plaintext changed. The update is optimistic on `baseRevision`; active covering grants are paged completely and refreshed against the exact new revision in the same transaction. Policy tightening may narrow an existing grant scope, while missing, stale or broadened envelope context fails closed before commit.

Credit Card is canonical entry type `3`. Its MemberSecret contains cardholder name, PAN, expiry month/year and billing address. Dedicated card security-code and PIN fields are intentionally unsupported; general custom fields remain neutral and receive no card-specific recognition. Credit Card is excluded from public `palladin.grant-payload.v1`: current policy defaults every card field to `never`, grant UI/callers do not offer a card target, and Script references cannot select card fields. Existing legacy internal records remain readable but cannot be refreshed or widened into a new public v1 Grant. MemberIndex contains only presentation metadata. Script uses its runtime projection; Key and Credential use the standard registered Grant fields. Import/export preserves the supported card storage schema, while plaintext buffers and export intermediates are wiped with the other secrets. The Create Entry selector defaults to and lists Credential first, followed by Key, Script and Credit Card.

Script entries carry a required Agent-visible description, a typed parameter schema and an explicit `returnResultToAgent` policy inside encrypted MemberSecret/AgentDiscovery projections. New Scripts default result return to enabled; a legacy missing flag remains disabled. Parameters contain definitions only — values arrive from the Agent runtime and never reach the web/backend request path. References are same-Vault, unique by case-insensitive environment name, exclude Script/self targets and reject process-control names such as `PATH`, `LD_*`, `NODE_OPTIONS`, `PALLADIN_*` and `CLAW_*`. Source Entry schemas are decrypted locally so credentials, keys, cards, notes, custom fields and TOTP can be selected without exposing selectors or values to the backend.

When a Script, its references, description, parameter schema or result policy changes, Entry Detail requests a value-free access impact and warns with direct/FULL Agent counts before save. The canonical update includes replacement packages for the exact active direct ScriptExecution grants affected by the changed Entry. The backend commits the new Entry revision and all packages together or rejects the operation; no partial stale Script package remains active.

Create/edit catalog selection and imports prepare their unique website hostnames through the authenticated catalog boundary before encryption. Import preparation completes before VK/VDK are opened. It has no wall-clock deadline and waits until every hostname reaches `Ready` or `Failed`; the durable queue can therefore drain even for large imports. Complete import/repair polling uses a bounded asynchronous three-second cadence and honors `Retry-After` without resetting accumulated progress. Existing-host readiness checks do not consume the backend acquisition quota, which is charged only for newly reserved hostnames. The import modal remains mounted across responsive layout changes so docking DevTools or resizing the window cannot detach the active mutation and replace progress with a fresh upload step. Entry-form previews retain their own bounded five-second phase. Only a catalog response with status `Ready` contributes `{ kind: "publicAsset", assetId, revision, url }` to `MemberSecret` and `MemberIndex`; `Failed` and catalog errors continue without an icon URL. Application subdomains retain their exact catalog identity. This is a pre-production clean cutover: test ciphertext containing the retired `{ kind: "website", hostname }` or id-only public-asset shape is intentionally reset rather than carried into the canonical schema. Catalog failure remains presentational and does not block credential persistence. Vault lists, Entry Detail, Dashboard and global search render the validated direct asset URL after decryption and never call resolve, ensure, by-id or get-by-id while reading Entries. Global search resolves encrypted custom Vault and Entry icons through the authenticated encrypted-asset pipeline, keeps plaintext image bytes in memory only, and revokes local object URLs when a result unmounts or the Vault locks. A failed image GET or encrypted-asset authentication failure falls back to the local type glyph immediately, without cache-busting retries or backend polling.

The import configurator exposes an explicit `VaultManage`-gated repair for active, authenticated Credential projections that have a `urlDomain` and no icon; the Entries list does not own this action. Repair remains a write flow, never a read-time lookup: it waits without a wall-clock deadline for all unique catalog hostnames to become terminal before opening Vault keys, then processes one canonical Entry at a time through the normal optimistic update and active-grant refresh path. The current MemberSecret is decrypted and revalidated before each update so a stale MemberIndex cannot replace a user-selected icon or mutate another Entry type. Lock-session changes abort the batch, individual corrupt/conflicted Entries are isolated, and one follow-up Member sync reconciles successful revisions.

The extension onboarding deep link `/vaults?intent=import` is resolved only after Member sync is authoritative. The panel selects the Vault carrying the server-owned `isDefault` marker, navigates to that exact Vault ID and opens the existing lazy-loaded Import Wizard. It never infers the default Vault from list order or decrypted display name. Login and unlock redirects preserve the intent.

Entry History is a separate lazy query mounted only while its tab is open. Pages contain ciphertext metadata plus the exact encrypted Entry-key envelope referenced by each immutable revision, which permits local decryption across Entry rekeys without exposing raw keys. User actor IDs resolve through the shared current/former organization member directory; Agent or unavailable actor IDs fall back to shortened prefix-and-suffix hints. A version is decrypted only after explicit reveal. Reveal renders the complete historical Entry as a read-only form — presentation, type-specific fields, custom fields, notes and Agent visibility policy — instead of an opaque revision summary or an ambiguous tab-level explanatory banner. Changing tabs, unmounting, or locking drops the selected plaintext, while temporary byte buffers are wiped. Restoring an old version uses the normal optimistic update path against the current head, including the historical color, so the old record is never mutated: the selected plaintext becomes the draft for a newly encrypted revision, and all active covering GRANULAR grant envelopes are refreshed atomically. FULL grants continue through their single Vault-key wrapper.

Archive restore decrypts one canonical MemberSecret at a time and appends a new immutable `restored` revision through the lifecycle endpoint. Discoverable Entries use the server-provided Discovery high watermark rather than the removed current projection, preventing revision reuse after archive. Bulk restore is deliberately sequential and bounded: every Entry is its own atomic backend transaction, isolated conflicts are reported per item, and the browser never retains an entire batch of decrypted secrets or EF-tracked aggregates. A lock or replacement unlock session stops the batch before any material prepared by the invalidated crypto session can be submitted.

Recently Deleted uses the cursor-paginated lifecycle endpoint in bounded pages of 100 and resolves labels only from the authenticated in-memory MemberIndex. The server supplies each retention deadline; the browser never duplicates the retention policy. A missing or corrupt local projection falls back to a shortened opaque Entry ID. Restore uses the same sequential authenticated revision flow as Archive. Permanent purge requires a dedicated confirmation and reconciles the local tombstone only after the idempotent, transactional server endpoint succeeds.

Entry Logs queries structural audit events by the composite opaque Vault and Entry IDs. Structured Agent/event/date filters are applied by the backend before cursor pagination, while free-text search stays local and is never sent as a content query. The fixed Entry label comes from MemberIndex; Agent and Member names come from local structural directories. Deleted or unavailable principals fall back to shortened prefix-and-suffix IDs. Rows reuse the canonical Audit event configuration, preserving the shared semantic color taxonomy and event meanings.

## Key patterns
- **Zero-knowledge on-demand:** the vault key is unsealed and the entry decrypted only at reveal/open time; plaintext lives in component `useState` and never leaves memory.
- **Strict Vault-detail binding:** the encrypted detail contract accepts the server-owned canonical `metadataRevision` and requires it to equal the authenticated Member Vault Metadata envelope revision before any key material is opened.
- **Crypto-session-scoped detail cache:** canonical Entry heads, Entry prefetches and encrypted Vault detail envelopes are keyed by the current non-secret `cryptoSessionGeneration`. `staleTime: Infinity` therefore applies only inside one unlock session; a later unlock must fetch a mutually current Entry/Vault envelope pair before decrypting.
- **Bounded Member sync:** pages contain at most 200 items, responses fail above 4 MiB, projection work runs in chunks of 25 with at most four concurrent AEAD operations, and each chunk yields to the browser. The unlocked account index fails closed above 10,000 actual heads; it is never silently truncated.
- **Atomic completeness:** snapshot pages build a private cache namespace; the namespace becomes active only after its closing delta commits. Each active delta page and cursor update share one IndexedDB transaction. `resetRequired` discards the pending namespace and rebuilds without exposing a partial view.
- **Offline local search:** the unlocked, normalized MemberIndex supports local search across 10,000 entries. Optimistic projections reconcile by monotonic MemberIndex revision and never write plaintext to IndexedDB.
- **Freshness:** while an unlocked tab remains visible and online, a non-overlapping incremental delta poll runs every 60 seconds; online and visibility transitions trigger an immediate refresh.
- **Staged member removal:** a successful DELETE means requested, not removed. The Members tab polls structural status without key material, distinguishes active processing from paused/error state, and exposes the last-capable-Member blocker without disabling normal Vault use.
- **Atomic encrypted Vault creation:** a server-issued opaque ID scopes one client-generated VK, VDK and private-key set. The create request contains encrypted metadata and key envelopes only; the resulting Vault enters the UI through normal Member sync. Custom presentation assets use the dedicated encrypted protocol-2 flow.
- **Create completion:** after the server confirms creation (or idempotent reconciliation finds the committed Vault), the dialog closes and routes directly to that returned Vault ID; it never guesses the new Vault from list ordering.
- Split-view layout (3 pages) and an inline entry-detail tab strip — both candidates for the shared `SplitView` / `DetailTabBar` (see component-catalog).
