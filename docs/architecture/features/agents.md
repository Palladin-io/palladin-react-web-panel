# Feature: agents

**Path:** `src/features/agents/`

## What it does
Manage the org's AI agents: review enrolment requests, approve/deny them, and inspect each agent's grants and audited activity.

## How it's organized
A split-view page — agent list (cards) on the left, agent detail on the right. The detail view has its own tab strip (Overview / Grants / Logs) and an always-visible inline-edit form gated by `canEdit`. Enrolment approve/deny are modal dialogs; the avatar and agent card are reusable pieces. The list also opens an Add Agent message dialog, while `/agent-pairing/$pairingId` owns the authenticated browser approval surface. Data comes from agents and pairing query hooks. The route composes the Audit-owned Logs panel through `renderLogs`, keeping the feature dependency one-way. The panel uses the org-scoped Audit API with a fixed server-side `agentId`, shared Audit filters/rows and cursor-based infinite loading; free-text search remains local over already loaded rows and locally resolved Member-index labels.

## Key patterns
- **Approval is a two-phase zero-knowledge flow** — the backend first activates the Agent identity, then the unlocked client immediately reconciles every current Vault: it opens the VDK and Vault signing material in memory, seals the VDK to the Agent X25519 key, signs the manifest and uploads ciphertext-only provisioning. The approval mutation remains pending through this reconciliation and reports an explicit pending-retry result if activation committed but provisioning failed.
- **Browser pairing** starts from either the direct runtime/CLI/MCP command or the Add Agent message. Add Agent is a single-screen dialog: its localized, ready-to-paste instruction and exact, shell-neutral `palladin pair-agent --host … --setup-descriptor …` invocation are visible immediately and update as the optional display name changes. The instruction tells the Agent to install the official Palladin CLI from `https://palladin.io/docs` when unavailable and always pair through that CLI; it never emits source-checkout or OS-specific development scripts. Only the API origin and optional validated display-name data are included; the latter is encoded in the canonical `PALLADIN_AGENT_SETUP_V1` descriptor; the descriptor never includes a secret or free-form instruction, and the raw display name never enters message prose or shell syntax. The CLI keeps final display name/type authoritative to the backend. The authenticated approval route uses the shared focus-trapped `ModalShell`, with a scrollable full-width form and a pinned `DialogFooter`. Dismissal leaves the request pending and preserves its cached claim for reopening the same deep link; rejection remains an explicit mutation. Controls and dismissal are disabled during mutations, including the complete awaited Discovery preparation that follows backend activation. The page claims the opaque handle once, shows the runtime-declared free-form type and editable name, reserves a localized friendly fallback when no name was declared, and lets the user select an existing logical API key or create one. Exhausted fallback suggestions degrade to accessible manual name entry rather than failing the request. Approval creates a standard active Agent; hidden child credentials never enter this frontend.
- Pairing claim is a mutating POST, so its successful React Query result is cached for the pairing lifetime and does not refetch on mount, focus, or reconnect. Reservation is repeated immediately before approval; 409 exposes only an availability conflict and never the colliding Agent.
- Add Agent derives its explicit non-secret `--id` from the display name: lowercase ASCII letters/digits and hyphens, diacritic normalization including Polish ł, at most 64 characters, and a safe prefix for Windows reserved names. A localized friendly name is proposed immediately and reused if the input is cleared. Names without any convertible Latin letters/digits are rejected for this CLI-message flow (direct pairing metadata remains unchanged). The profile preview is visible; collisions fail closed and require a different name, never overwrite. A later server display-name edit does not rename the local profile. After success the instruction requires workspace-local persistence of exact profile/host for future CLI/MCP use, without secrets, overwriting existing connection notes or changing the global default. Inability to persist must be reported.
- `MemberSyncProvider` repairs pending provisioning on unlock/mount, approval, online/visibility changes and a bounded interval. Creating a Vault also requests immediate reconciliation for every active organization Agent.
- Once provisioned to a Vault's current VDK, the Agent receives future discoverable Entry revisions through encrypted Discovery delta sync; secret delivery still requires a separate grant.
- Split-view + inline tab strip — candidates for shared `SplitView` / `DetailTabBar`.
- The detail tab strip stays pinned while each tab owns an internal `ScrollArea`; Logs additionally pins its search/filter chrome above the canonical audit list.
- `AgentCard` currently inlines its hover classes instead of `HOVERABLE_CARD_CLASSES` — align on next touch.

## Cross-feature deps
- **Exports `AgentCard`** (reused by `api-keys` Agents tab — the main card-level cross-feature reuse), plus `AgentAvatar` and the agents query.
- The approve/deny dialogs are reused by `notifications` for inline enrolment actions.
- The app route composes the Audit-owned Agent Logs panel; Agents does not import Audit. The feature consumes `grants` for the Grants tab.

- The legacy approval dialog also traps focus. Its type combobox portals its listbox to the body, keeps keyboard focus on the input, and consumes Escape before the modal; nested icon dialogs handle only their own dismissal.
- Browser-pairing approval leads with the standard Agent avatar, live display name and runtime type label; the shortened public key and expiry remain secondary metadata. The avatar opens the existing `AgentIconBrowser` for a glyph selection and restores keyboard focus on close. The optional `iconKey` is submitted with approval and saved atomically during standard activation; no follow-up profile mutation is needed.
- The same avatar picker also offers custom PNG/JPEG/WebP upload (maximum 1 MiB). Before approval, the file stays local with a revocable blob preview; neither the file nor its blob URL enters the pairing request. After activation returns an Agent ID, the existing icon upload/complete flow stores the public-asset reference. The dialog stays pending through upload and Discovery preparation. Upload failure never repeats or rolls back activation: an explicit toast directs the user to retry from Agent details. Selecting a glyph discards the pending file; replacement/unmount releases its preview URL.
